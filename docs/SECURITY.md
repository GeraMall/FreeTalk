# Безопасность и модель угроз

FreeTalk не имеет аккаунтов и серверной аутентификации. Обладающий действующим кодом комнаты человек может попытаться войти, пока есть свободное место. Случайный код снижает вероятность угадывания, но не делает комнату «полностью защищённой». Имена не удостоверяются.

WebRTC шифрует транспорт DTLS-SRTP между peers/relay. TURN видит зашифрованные пакеты и метаданные, но это не проверяемое пользователями end-to-end шифрование с identity keys. Скомпрометированный клиент может записать услышанное средствами ОС.

Реализовано:

- Zod-валидация всех сигналов, UUID/room/name форматов и SDP/ICE размеров;
- максимум 32 KiB на WebSocket message и 120 сообщений/10 секунд на соединение;
- максимум 6 участников, очистка пустых локальных комнат, 30-секундный reconnect grace в Worker;
- имена отображаются React text nodes, `dangerouslySetInnerHTML` отсутствует;
- строгая Tauri CSP, только `core:default`, без shell/fs/process plugins;
- нет remote code, analytics, telemetry, записи голоса, базы данных и секретов клиента;
- сервер не логирует SDP, ICE credentials, имена или содержимое сигналов.

Ограничения MVP: нет room password/host approval, identity verification, abuse bans и E2EE key verification. Для размещения в открытом интернете следующий security milestone — capability token комнаты, выдаваемый создателем, и отдельный invite token с TTL.
