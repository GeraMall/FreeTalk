# Работа без VPN в России

> Обновление 24.08.2026: клиентский production signaling перенесён с `workers.dev` на собственный WSS `freetalk.191-44-38-60.sslip.io:443` в Санкт-Петербурге. Cloudflare Worker остался только закрытым server-to-server broker для краткоживущих TURN credentials. Описание ниже до этого примечания фиксирует результаты прежней Cloudflare-схемы и сохранено как история диагностики.

Проверено 23.08.2026 на обычном Ethernet-подключении текущего ПК, принудительно
исключив VPN-маршрут для тестовых сокетов:

- production signaling и WSS Cloudflare Workers доступны на TCP 443;
- updater manifest на GitHub Releases доступен по HTTPS (HTTP 200);
- Cloudflare STUN вернул корректный Binding Response по UDP 3478;
- `turn.cloudflare.com` доступен по TCP 443, 80 и 3478.

Эти результаты подтверждают доступность сетевых точек через проверенного российского
провайдера, но не гарантируют одинаковую маршрутизацию у всех операторов и во всех
регионах. FreeTalk 0.3.4 дополнительно перезапускает ICE после получения серверной
TURN-конфигурации и ограничивает автоматические ICE restart тремя попытками.

## Что уже работает без TURN

Сигналинг, комнаты, присутствие и прямой WebRTC через STUN работают без VPN там, где
NAT двух участников допускает прямую пару. Сервер комнат не получает аудио.

## TURN для сложных NAT

Для symmetric NAT, части мобильных операторов и строгих корпоративных сетей нужен TURN.
Worker уже умеет выдавать только краткоживущие credentials и не передаёт долгосрочный
секрет клиенту. 23.08.2026 production Worker получил `TURN_KEY_ID` и
`TURN_KEY_API_TOKEN` как зашифрованные Cloudflare secrets. Значения не находятся в
клиенте, репозитории или логах. При невозможности получить credentials Worker безопасно
возвращается к STUN.

Автоматический Chromium-тест принудительно установил `iceTransportPolicy: "relay"` между
двумя WebRTC-пирами. Без VPN, через Ethernet, отдельно для UDP, TCP и TLS подтверждены
relay-кандидаты с обеих сторон, обмен данными, получение удалённого аудиотрека и
ненулевого тестового аудиосигнала.

Cloudflare на дату проверки указывает 1000 GB в месяц бесплатно для общего использования
Realtime SFU/TURN, затем тарификацию $0.05/GB. Это usage-based сервис, поэтому включать его
без согласия владельца на возможные расходы нельзя. Официальные источники:
[TURN pricing](https://developers.cloudflare.com/realtime/sfu/pricing/),
[TURN endpoints](https://developers.cloudflare.com/realtime/turn/),
[short-lived credentials](https://developers.cloudflare.com/realtime/turn/generate-credentials/).

Когда сервер выдаёт TURN-конфигурацию, интерфейс показывает «TURN готов» и
«WebRTC · TURN резерв».

Версия 0.3.6 запускает первое согласование уже с полученными TURN credentials,
буферизует ICE-кандидаты, пришедшие раньше SDP, и получает через DNS-over-HTTPS
актуальный IPv4-адрес `turn.cloudflare.com`. Сервер добавляет к официальным
TURN URL резервные UDP/TCP URL по IP на портах 3478, 53 и 80. Это помогает при
блокировке DNS-имени провайдером; TLS URL на 443 остаётся доменным, поскольку
проверка сертификата по IP невозможна. Если оператор блокирует саму сеть
Cloudflare TURN, гарантировать работу без второго независимого TURN-провайдера
нельзя.

Версия 0.3.7 добавляет контроль `pong`: если после смены VPN или
сетевого интерфейса WebSocket остался формально открыт, но сервер
перестал отвечать, клиент закрывает зависший сокет не позже чем
через 45 секунд и входит в комнату заново. События `online` и изменения
Network Information API запускают это восстановление сразу. После
получения нового `joined-room` WebRTC-пиры создаются заново уже на
актуальном маршруте.

Версия 0.3.8 переносит production WebSocket из WebView2 в нативную
Rust-часть Tauri. Это устраняет обнаруженную на Windows ситуацию, когда
встроенный браузер продолжал использовать VPN-маршрут и не мог заново
войти в комнату после отключения VPN, хотя обычный системный сокет через
Ethernet открывал тот же WSS. В release-сборке 0.3.8 проверено создание
production-комнаты и получение TURN-конфигурации; установленное TCP 443
соединение принадлежало процессу `freetalk.exe`, а не WebView2.

Версия 0.3.9 устраняет найденную после выпуска 0.3.8 потерю поздних
сигнальных сообщений между Rust и WebView. Входящие события теперь находятся
в очереди до явного последовательного получения интерфейсом, а исходящие
offer/answer/ICE также сохраняют порядок. Два отдельных Windows release-клиента
0.3.9 без VPN вошли в одну production-комнату: уже находившийся в комнате
клиент увидел поздний вход, оба показали `2 из 6` и получили удалённый
аудиотрек (`Слушает`).

Это подтверждает исправленный сценарий на проверенном Ethernet-провайдере,
но не является обещанием доступности любого оператора, страны или NAT.
Фактическая слышимость через реальные микрофоны/наушники в автоматическом
тесте не подтверждалась.
