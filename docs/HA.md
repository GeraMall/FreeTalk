# TRLKA: основной сервер и резерв

Состояние на 07.11.2026. Эта конфигурация создаёт тёплый резерв с управляемым
переключением. Автоматического повышения резервной базы до основной нет.

| Узел             | Публичный IP    | WireGuard  | Роль                                                     |
| ---------------- | --------------- | ---------- | -------------------------------------------------------- |
| HOSTKEY, Москва  | 185.225.201.129 | 10.73.54.1 | API, сигналинг, PostgreSQL primary, сайт, установщики    |
| RUVDS, Петербург | 191.44.38.60    | 10.73.54.2 | PostgreSQL standby, резерв файлов, legacy HTTPS/WSS шлюз |

WireGuard `trlka-ha` использует UDP 51820, разрешённый только между публичными
IP этих двух узлов. Внутренние PostgreSQL 5432 и HTTP 18080 доступны только
через туннель с адреса второго узла. API 8790 и сигналинг 8787 слушают loopback.
На новом VPS SSH-пароль отключён, работает ключ владельца и fail2ban.
Дополнительный ключ резерва ограничен WireGuard IP и `rrsync -ro` на каталог
экспорта; доступа к произвольным командам он не даёт.

## Что уже проверено

- Переключение с Петербурга в Москву выполнено при нуле активных комнат.
  Перед повышением московского standby старые службы остановлены, последняя
  подтверждённая WAL-позиция воспроизведена, старая база остановлена и fenced.
- После повышения Москвы Петербург пересоздан из `pg_basebackup` и запущен
  как standby. На момент проверки `trlka_petersburg | streaming | lag_bytes=0`.
- Отдельная подтверждённая тестовая запись появилась на standby; тестовая
  таблица затем удалена. Сервисная проверка запрещает запуск API на standby.
- API и сигналинг проверены на изолированной QA-базе без отправки писем и push.
- Публичные API, WebSocket ping/pong, TLS и блокировка внутренних API проверены
  по обоим публичным адресам. В ответах работающего узла `X-Trlka-Node: moscow`.
- SMTP-аутентификация проверена без отправки письма; TURN broker возвращает
  действительную конфигурацию relay с обычным TLS нового узла.
- Дамп восстановлен в отдельную QA-базу, затем QA-кластер остановлен.

## Репликация и копии

PostgreSQL 16.15, физическая асинхронная репликация, slot `trlka_petersburg`.
При аварийной потере primary последние ещё не переданные транзакции могут
отсутствовать на резерве. Нулевой текущий lag не гарантирует нулевой RPO в будущем.
Предел удержания WAL на primary — 512 MB; длительно отключённый standby может
потребовать повторного клонирования. Нельзя удалять WAL вручную.

`trlka-ha-export.timer` на primary и `trlka-ha-sync.timer` на reserve каждые
пять минут синхронизируют API, bundle сигналинга, конфигурацию приложения,
три каталога сайта/загрузок и копию TLS-хранилища. Скачивание сначала идёт в
закрытый staging; публикация выполняется только при роли reserve и standby DB.
Идентичные файлы связываются hard links для экономии диска. Нельзя добавлять
`--inplace` к rsync: он изменил бы связанные копии до завершения переноса.
Службы, версия Node и миграции инфраструктуры обновляются отдельно на обоих узлах.

`trlka-ha-backup.timer` каждый день в 03:15 UTC с разбросом до 10 минут создаёт
`pg_dump -Fc`, дамп ролей и SHA-256 в `/var/backups/trlka-ha` (root-only).
Хранятся 7 последних копий в Москве и 3 в Петербурге. Это две копии у разных
провайдеров, но не отдельное immutable/offsite-хранилище.

`trlka-ha-monitor.timer` каждую минуту проверяет роль DB, службы primary,
поток репликации и свободное место. Результаты находятся в systemd journal;
внешняя отправка оповещений не настроена. Ошибка проверки **не** повышает standby.

## Проверка состояния

На каждом сервере от root:

```sh
/usr/local/sbin/trlka-ha-monitor
systemctl list-timers 'trlka-ha-*'
journalctl -u trlka-ha-monitor.service -n 20 --no-pager
journalctl -u trlka-ha-sync.service -n 20 --no-pager  # на резерве
```

На primary:

```sh
runuser -u postgres -- psql -c "SELECT application_name,state,sync_state,pg_wal_lsn_diff(pg_current_wal_lsn(),replay_lsn) AS lag_bytes FROM pg_stat_replication"
```

API и сигналинг разрешено запускать только при `/etc/trlka-ha/role = primary`
и `pg_is_in_recovery() = false`. Это проверяет
`/usr/local/sbin/trlka-ha-primary-condition` в systemd ExecCondition.

## Выпуск приложения или API

Деплой выполняется на **185.225.201.129**, а не на старый IP из исторических
команд. После проверки production принудительно обновить резерв:

1. На primary: `systemctl start trlka-ha-export.service`.
2. После успешного export на reserve: `systemctl start trlka-ha-sync.service`.
3. Проверить оба журнала, одинаковые версии и свободное место.

Секреты `/etc/freetalk`, пароли репликации, `.pgpass`, SSH/WireGuard ключи и
TLS-хранилище не должны попадать в Git, вывод команд или публичные артефакты.
Файлы в `deploy/ha` — шаблоны операций; одноразовые bootstrap/clone-скрипты
не запускаются повторно на живом primary.

## Аварийное повышение Петербурга

Только для оператора. Потеря ping или SSH сама по себе не доказывает остановку
Москвы. Сначала выключить/fence московский VPS через независимую панель провайдера
и убедиться, что он не сможет принять записи после возвращения сети.
Без fencing повышать второй primary нельзя: это создаёт две расходящиеся базы.

После подтверждения fencing:

1. На резерве остановить `trlka-ha-sync.timer` **и** `trlka-ha-sync.service`,
   проверить состояние PostgreSQL и последнюю принятую WAL-позицию. Оценить RPO.
2. Сохранить текущие конфигурации и новый дамп. Проверить
   `/root/trlka-ha/Caddyfile.failover` и свежесть `snapshot-at` в
   `/var/lib/trlka-ha-standby-files`. Подготовленный failover Caddy обслуживает
   сайт и обе API hostname локально, без московского приватного listener.
3. Выполнить `SELECT pg_promote(true,60)` от postgres. Проверить
   `pg_is_in_recovery() = false`, затем установить роль `primary` в
   `/etc/trlka-ha/role`.
4. Проверить сертификаты сайта в резервном TLS-хранилище. Копировать актуальные
   пары certificate/key для trlka.com и www.trlka.com из staging, сохраняя
   действующие собственные сертификаты legacy sslip и чужих сервисов Петербурга.
   Выставить владельца caddy. Не заменять всё TLS-хранилище старой копией целиком.
5. Проверить и установить failover Caddyfile, запустить API и сигналинг;
   проверить JSON health, WSS и внутренние запреты, затем переключить Caddy.
6. Изменить A-запись trlka.com на 191.44.38.60. Это влияет на сайт; старые
   клиенты с legacy адресом уже попадут на Петербург. Перезапущенные комнаты
   не сохраняются: звонки и присутствие сейчас находятся в памяти процесса.

Москва после аварии не запускается со старой primary-базой. Возвращать её только
как заново синхронизированный standby (`pg_rewind` при выполнении его условий
или `pg_basebackup` с сохранением старого каталога), затем отдельно планировать
обратное переключение. Не запускать старую primary и не включать два API сразу.

## Что ещё ограничивает отказоустойчивость

- Установленные клиенты и текущий публичный web build используют legacy sslip
  hostname, закреплённый за Петербургом. При падении Петербурга они не смогут
  автоматически выбрать московский endpoint. Требуется отдельное обновление
  клиентов, allowlist Rust, CSP и выбора endpoint. Одно изменение DNS trlka.com
  этого не исправляет. Прямой московский endpoint уже имеет рабочий HTTPS/WSS.
- Автоматический failover DB требует проверенного независимого арбитра/fencing,
  маршрутизации клиентов и полного теста отказов. Два VPS с наивным переключением
  по недоступности сети для этого небезопасны.
- DNS-кэши держат старый ответ до истечения ранее выданного TTL (до 86400 секунд
  для исходной A-записи). Старый сервер оставлен работающим шлюзом совместимости.
- На петербургском диске 20 GB мало запаса; контролировать место и не хранить
  новые дубликаты установщиков/неограниченный WAL. Увеличение ресурсов не оплачено.
