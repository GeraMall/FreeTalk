# Подключение новых серверов и восстановление TRLKA

Это подготовка программной части и установки. Она не включает покупку серверов,
изменение DNS или включение кластера на действующей инфраструктуре.

## Что подготовлено

- Голосовые узлы регистрируются в общем PostgreSQL, сообщают о готовности и лимите комнат.
- Маршрутизатор направляет участников одной комнаты на один узел. При истечении права
  владения другой узел восстанавливает комнату из сохранённого состояния.
- Сохраняются время начала, владелец, идентификаторы участников, состояние микрофонов
  и последние сообщения комнаты. Аудио, видео, SDP и ICE-кандидаты не сохраняются.
- Подтверждения изменения комнаты отправляются после записи состояния. Идентификаторы
  сессий хранятся в виде SHA-256, а не открытым текстом. Повторный вход всё равно проходит
  обычную проверку аккаунта/гостевого токена и соответствия сессии.
- Право записи ограничено сроком и номером поколения. Старый узел не может записать
  состояние после передачи комнаты другому. При потере доступа к БД узел закрывает
  управление комнатами после истечения своего локального срока.
- Плановые работы: `drain` запрещает выдавать узлу новые комнаты, но сохраняет текущие.
  Установщик отказывается обновлять узел с ещё активными комнатами.
- Вход и чаты используют один активный API и резервные экземпляры. Лидер выбирается
  через БД; остальные отвечают 503, поэтому локальные WebSocket-хабы не расходятся.
- Клиент звонка продолжает восстановление после длительного сбоя, использует разброс
  интервалов повторных попыток и тайм-аут открытия соединения.

Это первый этап: горизонтально распределяются комнаты. API работает в режиме
«основной/резервный», а не принимает нагрузку одновременно всеми экземплярами.
Гарантированная ёмкость на 500 или 10 000 пользователей этим не заявляется.

## Обязательные условия перед включением

1. Минимум два узла у независимых провайдеров, с запасом мощности на отказ одного.
2. Отдельный высокодоступный PostgreSQL с единственным действующим primary,
   сохранением подтверждённых записей при переключении и защитой от двух primary.
   Асинхронную копию с потерей последних записей нельзя считать безопасной заменой
   для таблиц владения. Один PostgreSQL на том же RUVDS оставит общую точку отказа.
3. Шифрованная приватная сеть между узлами: WireGuard или эквивалент. Порты 8786,
   8787, 8790 и PostgreSQL не должны быть доступны из интернета. Внутренние URL в
   примерах — адреса этой сети. Не заменять их публичными IP без TLS и ограничения доступа.
4. Два независимых внешних входа с HTTPS и проверкой здоровья через выбранный сервис
   балансировки/отказоустойчивого DNS. Единственный HAProxy или единственный Caddy
   на текущем сервере не обеспечивает защиту от отказа всего сервера/провайдера.
5. Общие секреты аккаунтов на API-репликах: TOKEN_PEPPER, INTERNAL_SIGNALING_SECRET,
   IP_HASH_SALT, ключи VAPID и доступ к одинаковой БД. На голосовых узлах — тот же
   INTERNAL_SIGNALING_SECRET. Секреты не входят в архивы и не передаются через Git.
6. Резервные копии аккаунтов, сообщений и файлов у другого провайдера с проверенным
   восстановлением. В текущем API аватары и вложения хранятся в PostgreSQL.
7. Действующие TURN-конфигурация и учётные данные на всех узлах. Этот этап восстанавливает
   управление звонком; он не обещает незаметную миграцию уже работающего TURN-соединения.

База и сеть должны быть подготовлены до старта узлов. TLS сертификаты БД проверяются:
`SIGNALING_CLUSTER_DATABASE_SSL=true` / `DATABASE_SSL=true`. Используйте доверенный CA;
не добавляйте в строку подключения параметры, отключающие проверку сертификата.

## Сборка и первоначальная установка

Из корня репозитория с зависимостями из lockfile:

```sh
pnpm install --frozen-lockfile
pnpm check
node scripts/deploy/build-cluster-artifacts.mjs
```

Получаются `outputs/cluster/trlka-cluster-node.tar.gz` и файл SHA-256. Архив включает
голосовой узел, маршрутизатор, административную команду и systemd-шаблоны. Он не
включает Node.js, HAProxy, приватную сеть, базу, веб-клиент или account API.

На новом Ubuntu-узле заранее установить тот же проверенный Node.js 22, что используется
для API (`/opt/node-v22/bin/node`), настроить приватную сеть, HAProxy и firewall.
Ключи SSH/VPN должны быть индивидуальны для машины, их нельзя запекать в общий образ.

1. Подготовить `/etc/trlka/cluster.env` по `deploy/cluster/cluster.env.example`,
   владелец `root:root`, права `0600`. Для каждого узла задать уникальные NODE_ID,
   приватные NODE_URL, SIGNALING_HOST и GATEWAY_HOST.
2. Один раз применить кластерную схему с административным доступом к БД:

```sh
set -a
source /etc/trlka/cluster.env
set +a
/opt/node-v22/bin/node /path/to/unpacked/cluster-admin.mjs migrate
```

После миграции runtime-ролям выдаются только нужные права: узлам SELECT/INSERT/UPDATE
на `signaling_nodes`, `signaling_rooms`; маршрутизаторам достаточно SELECT. DDL и
доступ к аккаунтам/паролям голосовым узлам не нужны.

3. Развернуть account API из актуального зафиксированного архива, используя существующую
   процедуру `scripts/deploy/build-production-server-artifacts.ps1` и Linux `npm ci`.
   Для нового хоста создать `/opt/freetalk/api`, распаковать архив, установить зависимости
   из его package-lock, применить миграции и установить `deploy/vps/freetalk-api.service`.
   Настройки из `deploy/cluster/api.env.example` дополняют существующие security/SMTP
   параметры; они не заменяют весь api.env. Применить миграцию 020 до включения
   API_HIGH_AVAILABILITY. Статус 503 у резервного API ожидаем: он станет готов после
   истечения права активного. Обычная проверка `/health` готова только у лидера.
4. Проверить и установить HAProxy-конфигурацию по `deploy/cluster/haproxy.cfg.example`.
   Внешний listener 8800 принимает запросы только с локального HTTPS-прокси, 8801
   используется исключительно локальными службами для внутренней авторизации.
   Проверить `haproxy -c -f /etc/haproxy/haproxy.cfg` перед reload. Сохранить текущие
   правила Caddy для CSP, загрузок, WebSocket и запрета `/api/v1/internal/*`.
   Фрагмент `deploy/cluster/Caddyfile.routes.snippet` сохраняет путь `/api/` до HAProxy:
   здесь нельзя использовать прежний `handle_path`, иначе префикс удалится дважды.
   В API_TRUSTED_PROXIES указывать только конкретные доверенные прокси. Внешний
   балансировщик и Caddy должны корректно проверять/перезаписывать forwarded-заголовки.
5. Передать архив и отдельно проверенную SHA-256. На узле запустить:

```sh
bash /path/to/unpacked/install-node.sh /path/to/trlka-cluster-node.tar.gz EXPECTED_SHA256
```

Установщик проверяет хеш и Node.js, размещает отдельную версию, переключает symlink,
устанавливает службы и проверяет готовность. Он не покупает услуги, не открывает
firewall и не изменяет DNS. Архив account API устанавливается отдельно.

## Добавление следующего голосового сервера

После первоначальной настройки общей БД, приватной сети и внешних входов:

1. Подготовить машину/образ, её индивидуальные сетевые ключи и cluster.env.
2. Установить проверенный архив той же командой `install-node.sh`.
3. Проверить список: `node cluster-admin.mjs status`. При необходимости выполнить
   `node cluster-admin.mjs resume voice-c`.

Новый готовый голосовой узел автоматически участвует в размещении комнат; список
серверов в приложении и конфигурацию маршрутизаторов для этого менять не нужно.
Отдельно добавлять новый gateway/API в HAProxy требуется только при расширении этих
слоёв. NODE_CAPACITY — предел комнат для допуска новых подключений, не измеренная ёмкость.

Для обслуживания: `node cluster-admin.mjs drain voice-a`, дождаться нулевого числа
комнат, выполнить `assert-empty voice-a`, обновить, проверить ready и затем `resume`.
При неудачном обновлении сохранить drain, вернуть symlink на предыдущий проверенный
release и перезапустить службы. Старый код без поддержки кластерного хранилища нельзя
запускать за кластерным маршрутизатором.

## Подключение клиентов и переключение

После проверки двух внешних входов собрать отдельный новый клиент/веб-релиз с
`deploy/cluster/desktop.env.example`: API и WebSocket должны использовать стабильный
`trlka.com`, а не имя с IP одного сервера. Текущую сборку 175 автоматически способной
пережить отказ её жёстко заданного IP считать нельзя. Старые релизы не подменять.

По умолчанию право владения — 15 секунд, heartbeat узла — до 3 секунд, окно
восстановления — 120 секунд. Клиент добавляет свои интервалы обнаружения и повторных
подключений. Это параметры алгоритма, а не гарантия восстановления за 15 секунд.
После окончания окна без участников комната не восстанавливается бесконечно.

Сначала включить режим в тестовом окружении, затем на двух узлах с проверкой реальных
Windows/iOS/Android-звонков, и только после этого переводить рабочий сервис. Начинать
следует с безопасного лимита и измерять CPU, память, задержки БД и трафик TURN; запас
должен обеспечивать работу при потере одного узла.

## Проверки

`Cluster failover` в GitHub Actions запускает отдельный PostgreSQL 17. Подготовлены
проверки конкурентного владения, смены поколения, запрета старой записи, drain,
истечения комнаты, выбора API-лидера и реальных WebSocket-процессов через gateway.
В сквозном тесте процесс владельца завершается SIGKILL; повторный вход проверяет
сохранение времени начала, владельца, выключенного микрофона и истории комнаты.

Локальный запуск DB-тестов требует отдельной БД именно с именем `trlka_cluster_test`:

```sh
CLUSTER_TEST_DATABASE_URL=postgres://test@127.0.0.1:5432/trlka_cluster_test pnpm --filter @freetalk/signaling test
```

Эти тесты очищают только явно выделенные тестовые таблицы. Без переменной DB-тесты
пропускаются. Никогда не задавать им production URL. Они проверяют сервер управления,
а не передачу реального аудио/видео и не подтверждают нагрузку на 10 000 пользователей.
