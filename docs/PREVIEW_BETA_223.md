# Preview beta.223: демонстрация экрана на Mac

08.11.2026, ветка `preview/macos-screen-quality-beta223`, исходники `a47adfa`.
Включает исправление чата комнаты из beta.222. Публичный выпуск остаётся beta.221.

## Сценарий

Друг показывает экран с Mac: режим «Видео», 1080p, 60 FPS, адаптивное качество
включено. На скриншоте получателя фактическое изображение 106×68 при 29 FPS.
До этого workaround Mac применялся только к balanced, преобразуя его в text.
Режим video оставался с `maintain-framerate`: WebKit мог дополнительно снижать
разрешение помимо ограниченного собственного адаптивного профиля TRLKA.

## Изменение

- Для всех режимов демонстрации Mac применяется `maintain-resolution`.
  Выбранные 1080p/60 FPS и режим video сохраняются; собственная адаптация TRLKA
  по-прежнему меняет битрейт/FPS/scale при плохой сети. Нельзя обещать постоянные
  1080p/60 FPS на любом соединении.
- После SDP и перехода соединения в connected параметры отправителя Mac
  повторно считываются и применяются. Это покрывает отказ setParameters до
  появления согласованных encodings, даже при отключённой адаптации/нулевом уровне.
- Отказы настройки отправителя больше не теряются: в локальной диагностике
  сохраняется тип ошибки без содержимого SDP/адресов.
- Диагностика различает captureWidth/captureHeight и отправляемое разрешение.
- Камера, политика демонстрации Windows и серверы не изменялись.

Рекомендация WebKit по аналогичному сценарию:
[bug312472](https://bugs.webkit.org/show_bug.cgi?id=312472).
Это обоснование обхода известного поведения, а не подтверждение точной причины
на устройстве друга без его локальной диагностики.

## Ещё не устранённые сообщения пользователя

Переключение на «Текст»/30FPS улучшило изображение на Mac — подтверждено владельцем.
Затем заявлен отдельный сбой: после остановки демонстрации повторный выбор экрана
показывает чёрное превью/вечную загрузку. Владелец сообщил, что с выключенной
передачей звука это тоже происходит; звук на Mac вообще не слышен.
Поэтому сбой нельзя приписывать только аудиозахвату или считать исправленным
новой политикой качества. Нужна локальная диагностика после воспроизведения.
Варианты setParameters/первого кадра/getDisplayMedia/захвата аудио без лога
пока лишь гипотезы. Новые правки этого пути в beta.223 не заявлены.

При аудите обнаружено: нативные start/stop аудио сейчас синхронные Tauri-команды,
start ждёт ready_receiver.recv() без таймаута; JS ждёт AudioContext.resume().
Это потенциальные блокировки для последующей проверки, не подтверждённая причина.
Не делать очередную сборку/релиз с обещанием починки повторного старта без проверки.
