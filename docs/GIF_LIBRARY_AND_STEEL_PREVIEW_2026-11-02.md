# TRLKA beta.177: локальный просмотр

Работа основана на публичной beta.176. Владелец одобрил на сравнительном изображении стальной синий `#8da6dc` и попросил заменить им бирюзовый акцент во всём приложении. Обновлены кнопки, обводки, фокус, декоративные градиенты и связанные состояния в общей Windows/веб-теме. Фотографии и логотип не перекрашены; зелёные статусы, предупреждения и красные действия сохраняют смысл. Боковая панель получила ровный тёмный фон и более светлые подписи. Прежняя компоновка сохранена; unslop не использовался.

Фон боковой панели уточнён по последнему скриншоту владельца: `#020914` по всей высоте. Стальной акцент относится к выделению и элементам управления, а не к осветлению фона.

По AGENTS.md новый интерфейс сначала передаётся владельцу отдельной Windows-сборкой. Ветка `preview/gifs-steel-20261102` не меняет публичный updater, сайт или latest release. Серверное дополнение API обратно совместимо с beta.176.

## Свои GIF и избранное

Для проверки обмена собственными GIF обеим сторонам нужна beta.177: beta.176 ещё не умеет авторизованно загружать новый тип вложений. Общий выпуск клиента следует делать согласованно после просмотра владельцем.

- Отправка `.gif` через окно GIF, обычное вложение, вставку и перетаскивание файла. Оригинальная анимация сохраняется без перекодирования.
- Загруженный GIF автоматически сохраняется в личную коллекцию. Получатель может добавить его из сообщения, повторно отправлять и использовать после удаления исходного сообщения.
- Свои файлы не публикуются в общем каталоге и не передаются внешнему GIF-сервису. Доступ к файлу проверяется по аккаунту: автор, собственное избранное или участие в чате с действующим сообщением. Знание UUID/ссылки само по себе доступа не даёт.
- Библиотека хранится на сервере и привязана к аккаунту, а не конкретному компьютеру. Заголовок/исходное имя файла хранится отдельно в избранном каждого пользователя: дедупликация не раскрывает имя чужой загрузки.
- Старые сообщения Wikimedia продолжают читаться. Ошибки недоступности, формата и размера различаются; недоступный URL больше не называется слишком большим файлом.

## Ограничения ресурсов

Ограничения защищают текущий небольшой сервер. Это предохранители, а не гарантия отсутствия любой нагрузки. При росте аудитории нужны отдельное объектное хранилище, закрытая CDN-раздача, общие распределённые ограничения и мониторинг свободного места.

| Ограничение                      | Значение                                                               |
| -------------------------------- | ---------------------------------------------------------------------- |
| Оригинал                         | до 30 МиБ                                                              |
| Формат                           | настоящий анимированный GIF, минимум 2 кадра                           |
| Размеры / сложность              | до 4096×4096, 1200 кадров, сумма площадей кадров до 160 млн пикселей   |
| Миниатюра                        | до 64 КиБ и 360×360; клиент формирует до 320×320                       |
| Хранение оригиналов и миниатюр   | до 128 МиБ на автора, 512 МиБ суммарно                                 |
| Избранное                        | до 200 записей на аккаунт                                              |
| Попытки загрузки                 | 12 в час на аккаунт, 120 суммарно                                      |
| Загрузка за 24 часа              | 128 МиБ на аккаунт, 1 ГиБ суммарно                                     |
| Скачивание за день               | 1 ГиБ на аккаунт, 10 ГиБ суммарно                                      |
| Одновременная загрузка оригинала | 1 на процесс, 20 с бездействия / 120 с общей длительности              |
| Одновременная выдача             | до 8 ответов и 64 МиБ суммарно зарезервированных тел файлов на процесс |
| Клиентские загрузки своих GIF    | не более 2 одновременно                                                |

До чтения тела резервируется дневной объём загрузки. Резервации и глобальные лимиты используют транзакции PostgreSQL: параллельные запросы не обходят бюджет. Недопустимые загрузки тоже учитываются. Одинаковые оригиналы хранятся один раз по SHA-256. В каталог загружаются небольшие миниатюры; полная анимация — по наведению/фокусу. В чате изображения загружаются только около видимой области; GIF исключены из предварительной загрузки всей истории. Клиентский кэш ограничен существующими бюджетами (64 МиБ в памяти, 128 МиБ на диске аккаунта).

Каждые 15 минут удаляются неиспользуемые файлы, на которые нет избранного и действующих сообщений, с часовым запасом от гонки очистки. Логи квот хранятся два дня. При заполнении хранилища новые загрузки останавливаются; существующие сообщения и обычные звонки продолжают работать. Ошибки лимитов выводятся в интерфейсе понятным текстом.

Семафоры передачи сейчас рассчитаны на один API-процесс. Бюджеты хранения и трафика общие через PostgreSQL. При добавлении реплик нужно либо делить лимит памяти между ними, либо вынести выдачу файлов в объектное хранилище; текущее ограничение памяти не является общим между процессами.

## Подготовленное подключение KLIPY

Ключа пока нет: поиск честно сообщает, что ещё не подключён. Личные GIF и избранное от него не зависят. Не используются чужие/публично найденные ключи.

После получения собственного ключа и согласования production-доступа задаётся `KLIPY_API_KEY` в окружении API. Это **клиентский ключ**, выдаваемый авторизованному приложению; нельзя подставлять секрет, который провайдер запрещает передавать браузеру. Нужно ограничить разрешённые приложения/домены в кабинете провайдера. Веб-CSP перед публичным включением должен разрешить `api.klipy.com` для запросов и `static.klipy.com` для изображений. Tauri CSP уже подготовлен.

Поиск и медиа идут напрямую от клиента к API/CDN провайдера. TRLKA не скачивает, не проксирует и не хранит внешний банк. Сохраняются исходные URL, параметры доставки, порядок результатов и attribution Powered by KLIPY. Перед включением проверить контракт реального ключа, квоту, CORS, обязательные события/брендинг и условия хранения избранного; при необходимости согласовать отдельную вкладку внешнего избранного. Локальные GIF не смешиваются с результатами внешнего поиска.

## Другие исправления

- Активный звонок считается активностью: автоматический статус остаётся online при отсутствии движений мыши. После выхода обычный 10-минутный таймер запускается заново. Ручные «Невидимка», «Не беспокоить» и «Неактивен» сохраняются. Настоящий обрыв сети не маскируется ложным online.
- Кнопка «Отменить запрос» доступна только отправителю ожидающего запроса. Отмена видна обеим сторонам через realtime; можно отправить запрос заново. Одновременные принятие и отмена разрешаются атомарно.

## Проверка и перенос

- `pnpm check`: форматирование, линтер, типы, тесты и production-сборка.
- 12 сценариев на настоящем PostgreSQL в отдельной одноразовой БД: поддельный/статический файл, оригинальные байты, миниатюра, ACL, сохранение/переотправка, дедупликация и приватность имени, заполненное хранилище, конкурентные квоты, отмена/принятие запроса и очистка. Скрипт `scripts/qa/gif-postgres-audit.mjs` отказывается запускаться на БД без префикса `trlka_gif_qa_`.
- Визуальная и поведенческая проверка WebKit на ПК 1366×900, планшете 820×1180, телефоне 390×844: окно GIF, отправка, понятный отказ 429 и повтор, избранное, отмена запроса и отсутствие горизонтального выхода за экран.

Для будущего Android-клиента повторно использовать серверный контракт, приватный доступ с Authorization, лимиты оригинала/миниатюры, account-scoped кэш, ленивую загрузку, разделение собственного и внешнего источника, статусы активности звонка и токены `#8da6dc`/семантических цветов. Бинарные файлы не отправлять через realtime. Нативные Android/iOS экраны этим изменением ещё не перекрашены.
